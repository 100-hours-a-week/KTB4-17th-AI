## 1. F6 문서 요약

F6는 줄 단위 시뮬레이션이 대본을 끝낸 뒤, 이미 계산된 궁합 점수를 설명하는 서술 한 번의 품질을 본다. 대상 함수는 `ReportAgent.write`다. 문서는 라우트를 `POST /ai/api/v1/simulation`의 마지막 서술 단계와, LLM을 부르지 않는 `GET /ai/api/v1/simulation/{id}/report`로 적는다. 타임아웃은 `simulation_narrative_timeout_s` 60초다.

프롬프트 계약은 일곱 가지다.

1. 출력은 `ReportNarrative` JSON이다. 필드는 `headline`, `summary`, `area_comments` 다섯 영역, `highlights`, `strengths`, `cautions`, `date_comment`, `ideal_fit`이다.
2. 코드가 넘긴 점수를 바꾸지 않고, 대화록으로 이유를 설명한다.
3. 예외는 `ideal_warmth`, `ideal_vitality`, `ideal_status`뿐이다. 근거가 없으면 키를 빼거나 `null`이다.
4. `highlights.quote`는 대화록 원문의 부분 문자열이고, `turn_index`는 그 발화 번호다. `click`과 `friction`을 섞어 3~5개다.
5. A의 성향·발언을 B의 것으로 바꾸지 않는다.
6. 양쪽이 읽는 글이므로 한쪽을 깎지 않는다. "~해요" 체이고, 조언은 행동 단위다.
7. 신뢰도 `LOW` 차원은 "아직 잘 모르겠지만"으로 유보한다.

오류는 치명 4, 중대 3, 경미 2다. 치명 코드는 점수 위변조(E6-CRIT-01), 인물 전도(E6-CRIT-02), 가짜 인용(E6-CRIT-03), 템플릿 폴백(E6-CRIT-04)이다.

데이터는 0건이다. v1.13에서 `/report/preview` 24건이 빠졌고, 문서는 고정 대화록 24건(`simulation_narrative`, 표준 16 + 경계 8)을 새로 만들라고 한다. 자동 오라클 세 개는 점수 딕셔너리 완전 일치, 인용문·턴 인덱스 일치, 화자 키워드 비혼동이다.

게이트는 자동으로 점수 변경 0건, 가짜 인용 0건, 정상 대화록의 템플릿 비율 5% 이하다. 사람 검토는 정성 평균 3점 이상(5점 만점)과 인물 전도 0건이다.

## 2. 00 가이드라인 정합성

00의 기능 맵은 F6를 `ReportAgent.write()`로 고정한다. 기준서의 대상 함수와 같다. C5(리포트 점수 위변조 / 인물 전도)를 F6 치명으로 둔 것도 00의 기능 열과 같다. C1·C2·C3·C4·C6의 해당 기능 열에 F6가 없는 점도 기준서가 그 코드를 만들지 않은 것과 같다.

아래 여섯 가지는 00의 공통 규칙과 기준서가 어긋나거나, 기준서 안에 서로 다른 문장이 있다.

### 2.1 모델 점수와 제품 점수를 나누지 않는다

00은 가드레일·템플릿 적용 전의 원문(모델 점수)과 사용자에게 저장되는 텍스트(제품 점수)를 따로 집계하고, 둘을 평균하지 않는다. 집계표에는 `GUARDRAIL_MODE`(`shadow` / `enforce` / `off`)를 적는다.

기준서의 게이트는 점수 하나다. 템플릿 비율과 정성 평균이 같은 표에 있고, 어느 평균의 분모에서 템플릿을 빼는지가 없다. 가드레일 모드도 없다.

코드는 두 층이 실제로 다르다.

- 모델 원문: `ReportAgent.write`가 검증한 `ReportNarrative`.
- 제품 문장: `assemble_report`가 영역 점수·총점·위험 caution을 붙인 `MatchingReport`. `report_tool.write_matching_report`는 그 다음 범위 밖 `turn_index` 하이라이트를 지운다.

같은 출력을 한 점수로 보면, 필터로 사라진 인용은 모델 결함인데 제품에서는 "하이라이트 개수 부족"으로 보이고, 템플릿 문장이 매끄러우면 모델 평균이 올라간다. 00이 막으려는 왜곡이다.

### 2.2 템플릿 폴백의 등급이 00의 치명 정의와 다르다

00의 즉시 거절 치명은 C1~C6뿐이다. 폴백은 모델 점수 분모에는 실패로 넣고, 품질 평균 분자에는 넣지 않는다. 템플릿이 매끄러워도 모델 점수가 오르지 않게 하는 규칙이다.

기준서는 같은 사건을 E6-CRIT-04 치명으로 올리면서, 게이트에서는 5%까지 허용한다. 치명인데 0건이 아니다. 00의 집계 방식(분모 포함, 분자 제외)과도 다르다.

폴백으로 묶이는 원인도 하나다. `build_report`는 `LLMError`를 모두 템플릿으로 바꾼다. 타임아웃, 잘린 출력, JSON 파싱 실패, 스키마 실패, `enforce` 가드레일 실패가 같은 `narrative_source=template`이다. `shadow`에서 가드레일이 실패하면 템플릿으로 가지 않고 LLM 서술을 그대로 반환한다. 모드를 적지 않으면 5% 수치가 재현되지 않는다.

### 2.3 C5를 자동 0건과 사람 0건으로 쪼갠 뒤, 나머지 중대를 게이트에서 뺐다

00은 C5 하나라도 있으면 평균과 상관없이 게이트가 실패한다고 한다. 기준서는 점수 변경만 자동 0건이고, 인물 전도는 사람 검토 0건이다. 결과만 보면 C5는 둘 다 0건이라 00과 맞다.

가짜 인용은 00의 C-코드가 아니고 4.1의 결정적 검사(인용 부분 문자열)다. 기준서가 이를 치명·자동 0건으로 올린 것은 00보다 세다. 방향은 맞다. 다만 턴 인덱스 불일치(E6-MAJ-02)는 같은 인용의 다른 실패인데 게이트 표에 없다. 중대인 일방 비하(E6-MAJ-01)와 ideal 범위(E6-MAJ-03)도 게이트에 없다. 평균 3점과 인물 전도 0건만 통과하면 비하와 범위 이탈이 남아도 합격이다.

### 2.4 사람 척도 1/3/5의 앵커가 리포트에 그대로면 틀린 채점이 된다

00의 5점은 "자연스러운 메신저 구어체"다. 리포트 프롬프트는 분석 글이고 "~해요" 체다. 메신저 앵커를 그대로 쓰면 정상적인 리포트 문장이 1점이 된다.

`evals/quality_datasets/README.md`의 v1.12 기록은 옛 preview 리포트를 분석 문서로 보고, 몰입(20~30대 메신저 말투) 기준을 적용하지 않는다고 이미 정해 두었다. 설명 품질만 1/3/5로 보고 형식은 자동 지표로 봤다. 기준서는 그 예외를 되살리지 않은 채 "정성 평균 3점"만 적는다. 항목 가중치, 1/3/5 문장, 평가자 수, calibration/regression/holdout 분할이 없다.

00의 Judge 규칙은 calibration에서 사람 2인과 일치율 85% 이상인 뒤에만 regression 보조 채점을 허용한다. 기준서는 Judge를 말하지 않는다. 사람만 쓴다면 그 사실을 기준서에 적고, 2인 라벨을 완료 조건에 넣는다. Judge를 쓸 계획이면 24건을 분할 없이 두는 4.1절은 00과 맞지 않는다.

### 2.5 5단계 프로세스 중 골드셋과 전문가 검토가 비어 있다

00은 프롬프트 분석, 샘플 검토, 오류 분류, 골드셋 확정, 전문가 승인 뒤에 벤치마크를 고정한다. 기준서 v1.0.0은 1단계와 3단계 초안이다. 2단계 샘플은 "데이터 0건"이고 Langfuse 트레이스 검토 기록이 없다. 4단계는 작성 지침이지 확정 세트가 아니다. 5단계 승인도 없다. 게이트 숫자를 확정 기준으로 읽으면 00의 고정 조건보다 앞선다.

### 2.6 공통 결정적 검사 중 스키마·글자 수·이모지가 오류표에 없다

00의 4.1은 JSON 스키마, 필수 키, 글자 수, 금지 단어·이모지, 인용 부분 문자열, 차원 점수 불변을 자동 검사로 둔다. 기준서 자동 검사는 점수 불변과 인용뿐이고, 이모지·금지 단어·문장 수·영역 키 누락은 오류 코드가 없다. 글자 수는 헤드라인 30자만 경미로 있다. 스키마가 실제로 막는 상한은 3.2절과 다르다.

## 3. 코드·데이터셋 대비 오류와 수정안

심각도는 게이트를 잘못 통과시키거나 정상 서술을 실패로 만드는 항목을 높음으로 두었다.

### 3.1 높음 — 점수 완전 일치 오라클이 정상 경로를 실패로 만든다

기준서 1.2는 ideal 3차원만 모델이 매긴다고 한다. 4.2 `ruleScoresMustRemainUnchanged`는 "입력 점수와 출력 점수 딕셔너리 완전 일치"다. 두 문장이 동시에 성립하지 않는다.

`ReportNarrative`에는 영역 점수·차원 점수 필드가 없다. 추가 필드는 `extra = "ignore"`라 버려진다. 모델이 80을 50으로 "고친 딕셔너리"를 반환하는 경로는 없다.

점수가 바뀌는 정상 경로는 따로 있다.

1. `build_report`는 LLM 호출 전에 `score_layer(pa, pb)`를 돌린다. ideal 차원은 `None`이고, `_scores_section`은 그 값을 "미정"으로 프롬프트에 넣는다.
2. 호출 뒤 `assemble_report`가 `narrative.ideal_fit`을 넣어 `score_layer`를 다시 돌린다.
3. ideal 차원 점수, ideal 영역 평균, 총점이 호출 전 값과 달라진다. 총점은 `overall_score`에서 0~100으로 한 번 더 잘린다.

완전 일치 오라클은 ideal을 채운 정상 리포트를 전부 E6-CRIT-01로 떨어뜨린다.

사용자가 보는 숫자 위변조는 다른 층이다. 영역 `score`와 총점은 코드 소유다. 모델이 본문·`area_comments`·`why`에 다른 숫자를 적어도 저장되는 숫자는 그대로다. E6-CRIT-01의 예시 "80점을 서술에서 50점으로 변경"은 이 문장 모순이고, 출력 딕셔너리 불일치가 아니다.

수정안:

- 비-JUDGED 차원 점수는 호출 전 `score_layer`와 조립 후 리포트가 같은지 본다. 여기에는 `ideal_fit`이 끼어들지 못한다. `score_dimensions`는 `Fit.JUDGED`일 때만 `ideal_fit`을 읽는다.
- ideal 3차원은 모델 값 그대로인지, 그 값으로 영역 평균과 총점을 다시 계산한 결과와 리포트가 같은지 본다. 호출 전 "미정" 점수와 비교하지 않는다.
- 본문의 숫자가 코드 소유 점수와 모순되면 E6-CRIT-01로 둔다. 검사 대상은 `headline`, `summary`, `area_comments`, `strengths`, `cautions`, `date_comment`, `highlights.why`다.
- `ideal_fit`의 세 키 이외 키는 점수에 반영되지 않는다는 사실을 기준서에 적는다. 오타 키(`warmth`)는 조용히 미판정이 되므로, 근거가 있는데 세 키가 없으면 별도 중대로 둔다.

### 3.2 높음 — 길이·개수 기준이 프롬프트, 오류표, 스키마에서 세 갈래다

| 항목 | 프롬프트 (`narrative.py` `_REPORT_SHAPE` / `_REPORT_RULES`) | 기준서 오류표 | Pydantic `ReportNarrative` |
| --- | --- | --- | --- |
| headline | 20자 내외 | 30자 이상이면 경미. 같은 행 예시는 50자 이상 | `max_length=60`. 초과는 `ValidationError` → `LLMError` → 템플릿 |
| highlights 개수 | 3~5, click과 friction을 섞음 | 3개 미만 또는 5개 초과만 경미. 종류 혼합은 없음 | 최소 0, 최대 6. 7개부터 템플릿 |
| quote | 대화록 원문 그대로 | 부분 문자열 100% | 최대 200자. 일치 검사는 없음. 턴 본문 최대는 1000자라 긴 줄은 부분 인용만 스키마를 통과 |
| summary | 3~5문장 | 오류 코드 없음 | 최대 800자. 문장 수 검사 없음 |
| strengths / cautions | 예시 2개 | 없음 | 각 최대 5 |
| date_comment | 한두 문장 | 없음 | 최대 300, 기본값 `""` |
| ideal 값 | 0~100, 없으면 키 생략 또는 null | 범위 밖은 중대 | `dict[str, int \| None]`. `ge`/`le` 없음. 150과 음수를 받는다 |
| area_comments | 다섯 키 | 없음 | 임의 dict. 빠진 키는 조립 시 빈 문자열 |

스키마를 넘는 headline·highlights·kind는 경미나 중대가 되기 전에 E6-CRIT-04 템플릿이 된다. 기준서가 기대한 등급과 제품에 남는 결과가 다르다.

`ideal_fit` 150은 스키마를 통과하고 ideal 차원 점수가 된다. `grade_of`는 70 이상을 `GOOD`으로 본다. 영역 평균은 100을 넘을 수 있고, 총점만 0~100으로 잘린다. E6-MAJ-03은 지금 자동으로 막히지 않는다. `evals/quality_datasets/README.md`도 "ideal_fit은 현재 값의 0~100 범위 제약이 없다"고 적어 두었다.

수정안:

- 자동 형식 실패(스키마 초과, 잘못된 `kind`, JSON 파싱 실패)는 템플릿 사유로 모델 분모에만 넣는다. 경미 감점과 겹치지 않게 한다.
- 스키마 안에서 프롬프트를 어긴 것(headline 21~60자, highlights 0~2개 또는 6개, 종류가 한쪽으로만 있음, summary 문장 수가 3~5가 아님, 영역 키 누락, ideal이 정수인데 0~100 밖)만 형식 감점으로 둔다.
- headline 기준을 한 숫자로 정한다. 프롬프트의 "20자 내외"를 유지하려면 경미 기준도 20자 근처로 맞추고, 30자와 50자를 한 행에 두지 않는다. 60자는 스키마 하드 실패로 따로 적는다.
- quote 검사는 "해당 턴 `text`의 부분 문자열"로 확정한다. 턴 전체가 200자를 넘으면 전문 일치는 스키마상 불가능하다.

### 3.3 높음 — 인용 오라클의 인덱스와, 제품에 남기 전 필터가 다르다

기준서 오라클은 `transcript.turns[turn_index].text`의 부분 문자열인지 본다. 리스트 위치와 `Turn.index`가 같다는 전제다.

프롬프트는 `[turn.index]`를 모델에게 보여 준다. `report_tool`은 도구에 들어가기 전에 `enumerate`로 `index=i`를 다시 매긴다. 이 경로에서는 리스트 위치와 `Turn.index`가 같다. `ReportAgent.write`를 대화록 원본 인덱스로 직접 부르면 프롬프트의 번호와 `turns[turn_index]`가 갈라진다.

제품 필터는 인용 일치가 아니다. `write_matching_report`는 `0 <= turn_index < len(turns)`가 아닌 하이라이트만 지운다. 범위 안인데 다른 턴의 문장인 경우, 대화록에 없는 문장인데 인덱스만 맞는 경우는 저장된다. 범위 밖 가짜 인덱스는 제품에서 사라져, 모델의 인덱스 오류가 제품의 "개수 부족"(E6-MIN-01)으로 바뀐다.

수정안:

- 모델 점수는 필터 이전 `ReportNarrative.highlights`로 매긴다.
- 일치 조건은 `turn.index == highlight.turn_index`인 턴의 `text`다. 그 턴이 없으면 E6-MAJ-02, 턴은 있는데 `quote`가 부분 문자열이 아니면 E6-CRIT-03으로 나눈다.
- 제품 점수는 필터 이후로 따로 적고, 필터로 삭제된 개수를 사유에 남긴다.
- 평가 입력은 `report_tool`과 같이 0부터 다시 매긴 대화록으로 고정한다.

### 3.4 높음 — 인물 전도 자동 오라클이 현재 탐지기보다 세고, 프롬프트는 탐지기를 피한다

기준서 4.2 `noCrossSpeakerConfusion`은 "A의 고유 키워드가 B 설명에 쓰이지 않음"을 자동 100%처럼 적는다. 고유 키워드의 정의가 없다. "데이트", "좋아요" 같은 공유 단어는 오탐이 된다.

이미 있는 탐지기는 `agents._report_perspective_swap`이다. `report_tool`이 조립 후 본문에 돌리고 `validation.perspective_swap`에만 기록한다. 서술을 기각하지 않는다. 동작은 좁다.

- 속성은 `interests`, `routine`, `date_prefer`뿐이다. `date_avoid`, 점수 성향, 직업, 발화 원문은 보지 않는다.
- 길이 4 미만 속성은 건너뛴다.
- 상대 닉네임 뒤 40자 안에 그 속성이 있고, 그 사이에 주인 닉네임이 없을 때만 참이다.
- 검사 문자열에 `highlights.quote`와 `highlights.why`가 없다. 가드레일 텍스트(`narrative.py`의 `validate` 입력)도 같다. 인용 `why` 안의 전도는 두 검사 모두 밖이다.

F6 프롬프트 예문은 "A는 ~한 편이고 B는 ~한 편이라"다. 한 호출 시뮬레이션(`simulation/agents.py`의 `_REPORT_RULES`)은 반대로, 닉네임+님으로 부르고 `a`/`b`/`A`/`B` 기호를 금지한다. 기호 금지와 "프로필 기준으로 성향을 바꾸지 말 것"은 한 호출 쪽에만 있다.

F6 프롬프트를 따른 "A는 …" 문장은 닉네임을 찾지 못해 `perspective_swap`이 거짓으로 남는다. 한 호출 규칙을 F6에 들이대면, 프롬프트가 요구한 A/B 호칭이 실패가 된다.

수정안:

- E6-CRIT-02는 사람 판정으로 두고, 자동 오라클 완료 조건에서 내린다.
- 자동 신호는 기존 `perspective_swap`의 참/거짓과 한계(속성 종류, 4자, 40자, 하이라이트 미포함, 기각하지 않음)를 결과 필드에 남긴다. 참이어도 사람 확인 전 게이트 실패로 단정하지 않는다.
- 기준서에 F6 호칭 규칙을 명시한다. 현행 프롬프트는 A/B 예문이다. 닉네임+님을 품질 조건으로 올리려면 프롬프트 수정이 선행이고, 그 수정은 이 검토의 범위 밖이다.
- 한 호출 경로 `POST /ai/api/v1/simulation_old`의 리포트는 F6 점수로 넣지 않는다. 대본과 서술이 한 응답이고 규칙 문장이 다르다.

### 3.5 높음 — 템플릿·가드레일·잘림을 한 치명 코드로 두면 5% 게이트를 해석할 수 없다

`narrative.py`의 `build_report`는 에이전트가 없으면 바로 템플릿이고, `write`가 `LLMError`를 내면 템플릿이다. `report_tool`은 그 바깥에서 예외가 나면 에이전트 없이 한 번 더 `build_report`를 부른다. 보통의 LLM 실패는 안쪽에서 이미 템플릿이 되므로, 바깥 분기는 그 외 예외용이다.

템플릿 서술(`_template_narrative`)은 하이라이트가 없고 `date_comment`가 빈 문자열이다. 헤드라인은 잘 맞는 영역 이름을 잇고 60자로 자른다. strength·caution은 규칙 `why`와 위험 문장이다. 이 출력을 E6-MIN-01(하이라이트 3개 미만)에 넣으면 템플릿은 항상 경미 실패다.

`assemble_report`는 모델 caution 뒤에 위험 caution을 더하고 `[:5]`로 자른다. 모델이 caution을 5개 채우면 규칙 위험 문장이 제품에서 사라진다. README도 이 유실을 적어 두었다. 최종 리포트만 보면 모델이 위험을 뺐는지, 슬라이스가 잘랐는지 구분되지 않는다.

가드레일:

- `enforce`에서 `RETRYABLE`/`BLOCK`이면 `LLMError(reason="guardrail")` 후 템플릿. `last_validation`이 리포트에 남는다.
- `shadow`에서는 실패해도 LLM 서술을 반환하고 상태만 `SHADOW_FAIL`이다.
- `off`는 검사를 건너뛴다.
- 검사 문자열에 하이라이트와 `ideal_fit`이 없다.
- `_call_json`은 재시도가 없다. `max_tokens=1800`에서 `finish_reason=length`면 그 호출은 템플릿이다.
- 타임아웃 60초는 세마포어를 잡은 뒤 `_call`의 `asyncio.timeout`이다. 슬롯 대기는 그 밖에 있어서 벽시계는 60초를 넘을 수 있다.

수정안:

- E6-CRIT-04를 치명 즉시 거절에서 내린다. 00대로 모델 분모의 실패로만 집계하고 정성 평균 분자에서 뺀다.
- `narrative_source`와 함께 사유를 남긴다. `timeout`, `truncated`, `invalid_json`, `invalid_narrative`, `guardrail`, `unexpected`.
- 결과 표에 `GUARDRAIL_MODE`를 의무로 둔다. `shadow` 실패는 템플릿 비율에 넣지 않고 가드레일 실패로 따로 센다.
- 모델 caution과 조립 후 caution을 둘 다 저장한다. 위험 문장 유실은 코드 동작 케이스로 두고 서술 품질 감점에서 뺀다.
- 타임아웃 항목은 "슬롯 획득 후 호출 60초, 재시도 없음, max_tokens 1800, 슬롯 대기는 상한 밖"으로 고친다.

### 3.6 높음 — 데이터 0건은 맞다. 24건 설계는 실패 케이스가 없고 기존 파일을 재사용하면 안 된다

v1.13.0 manifest의 데이터셋은 다섯 개다. `persona_onboarding_conversation` 60, `persona_onboarding_tagging` 80, `persona_build` 60, `practice_reply` 70, `simulation_run` 36. `simulation_narrative`와 `simulation_report_preview` 파일은 없다. `humanReviewStatus=pending_dual_human_review`, Judge·실측·Langfuse 업로드는 미실행이다. 기준서의 "0건"과 "preview 24건 제거"는 README v1.13 문장과 같다.

재사용하면 안 되는 파일:

- `simulation_run.jsonl` 36건은 한 호출 대본(`simulation_old`) 입력이다. 리포트가 같은 응답에 섞여 있고 `ReportAgent.write`의 입력이 아니다.
- `simulation_line_draft.json`은 한 줄 대화 초안이다. `includeInMean`이 거짓인 F5 재료다.
- 삭제된 preview 24건은 `/report/preview` 입력이었다. 행을 되살려 F6 골드로 두지 않는다.

24건 설계의 빈칸:

- 00의 골드셋은 대표, 경계, 실패를 포함한다. 기준서는 표준 16과 경계 8만 있고 실패(깨진 JSON, 범위 밖 ideal, 가짜 인용, 인덱스 불일치, 가드레일 차단)가 없다.
- 분할이 없다. 00의 Judge 조건과 v1.13의 calibration/regression/blind_holdout 비율을 적용할 자리가 없다.
- "3~10턴"과 "3턴 이하"가 겹친다. 스키마 주석의 턴은 왕복이다. 10턴은 발화 20줄이다. 마이그레이션 기본값 `turns=10`도 왕복이라 완료 대화록은 20줄이다. 요청 최소는 3왕복(6줄)이다. "3턴"을 발화 3줄로 만들면 제품이 만드는 대화록과 다른 입력이 된다.
- 빈 대화록 분기가 빠졌다. 프롬프트는 턴이 없으면 "(대화록 없음 — 페르소나만으로 서술)"을 넣는다. 그 입력에 인용 3~5개를 요구하면 정상 유보와 날조가 구분되지 않는다.
- "LOW가 많은 프로필"이 점수 있음+LOW인지, 점수 `null`+LOW인지 없다. v1.4 이후 빈 차원의 규칙 점수는 `null`이다. 표시용 `a`/`b`만 50이다. 값 50을 모름으로 넣으면 C4 시절의 잘못된 상태가 된다.

수정안:

- 언어 품질과 `code_behavior`를 나눈다. 서술 품질은 고정 대화록에 `ReportAgent.write`만 호출한다. `POST /ai/api/v1/simulation` 전체는 대사 생성(F5)과 대기까지 포함하므로 F6 점수 호출로 쓰지 않는다. POST는 끝날 때까지 기다리고 리포트를 담은 `SimulationResponse`를 돌려준다. GET은 저장본이며 미완료면 409 `not_ready`다.
- 실패 fixture는 기대 사유(`timeout`, `invalid_narrative`, `guardrail`)와 템플릿 여부만 검사한다.
- 턴 수는 왕복으로 적는다. 표준은 제품과 같이 10왕복(20줄)을 포함하고, 경계는 최소 3왕복과 빈 대화록을 둔다. 3왕복을 표준과 경계에 동시에 넣지 않는다.
- 결손 페르소나는 모르는 차원 `scores=null`, `confidence=LOW`로 만든다.
- 케이스 수를 늘리더라도 분할 비율과 2인 라벨을 먼저 정한다. 24는 옛 preview 개수일 뿐 00의 확정 조건이 아니다.

### 3.7 중간 — 오류표에 없고 프롬프트에는 있는 실패

게이트에 넣기 전에 코드로 추가하는 항목이다.

- LOW 차원 단정. 프롬프트는 유보를 요구한다. 입력의 "근거 부족(LOW)" 목록과 본문의 단정 어투를 사람 항목으로 둔다. 코드는 이 어투를 검사하지 않는다.
- click/friction 혼합. 개수만 보면 click 4개가 경미를 통과한다.
- 빈 `area_comments` 값. 조립 결과는 빈 `comment`다.
- 프로필에 없는 나이·직업·거주지를 본문에 단정. 00의 C2 열은 F4·F5이고 F6가 아니다. 리포트 본문에도 같은 날조가 가능하므로, 00에 F6를 더할지는 가이드라인 쪽에서 정한다. 기준서만 치명으로 올리면 00의 기능 열과 다시 어긋난다.
- 프롬프트 20자 이상 복창(C6). 00은 F6를 C6 열에 넣지 않았다. 사용자 메시지에는 `_rules_section()` 전문이 들어가므로, 복창이 보이면 표본으로 남기고 C6 편입 여부는 00 개정에서 정한다.

### 3.8 기준서에 그대로 두어도 되는 부분

- 대상 함수가 `simulation_migration/narrative.py`의 `ReportAgent.write`인 점.
- GET 리포트가 LLM을 다시 부르지 않는 점. 미완료 409는 한 줄로 보완하면 된다.
- 호출 제한 시간의 설정 이름이 `simulation_narrative_timeout_s`이고 기본값이 60초인 점. 슬롯 대기와 재시도 없음만 덧붙이면 된다.
- 출력 필드 이름과 다섯 영역 키가 `_REPORT_SHAPE`와 같은 점.
- ideal 3차원만 모델이 매기고, 없으면 키 생략 또는 `null`을 둘 다 받는다는 점. 스키마 주석과 `score_dimensions`가 같다.
- 데이터셋이 현재 0건이고 preview 제거 이유가 v1.13이라는 점.
- 인용을 부분 문자열로 보려는 방향. 인덱스 정의와 필터 시점만 고치면 된다.
- 양쪽 공개 글, "~해요" 체, 구체적 조언, LOW 유보. 프롬프트에 있다. 오류 코드와 채점 앵커가 없을 뿐이다.

## 4. 기준서에 넣을 수정 문장 (초안)

원본은 바꾸지 않았다. 반영할 때의 교체 요지만 적는다.

1. 평가 호출은 고정 `Transcript`와 두 `PersonaResponse`로 `ReportAgent.write`를 부른다. 전체 `POST /ai/api/v1/simulation`과 `simulation_old`, `simulation_run.jsonl`은 F6 분모에서 제외한다.
2. 모델 점수는 가드레일·하이라이트 필터·`cautions[:5]` 이전 원문이다. 제품 점수는 `MatchingReport` 저장본이다. 둘을 평균하지 않는다. 표에 `GUARDRAIL_MODE`와 폴백 사유를 적는다.
3. 템플릿은 모델 분모의 실패이고 정성 평균 분자가 아니다. 비율 상한은 치명 0건 조건과 분리한다.
4. 점수 오라클은 "비-JUDGED 불변 + ideal_fit 반영 후 영역·총점 재계산 + 본문 숫자 모순"이다. 호출 전후 딕셔너리 완전 일치는 삭제한다.
5. 인용 오라클은 필터 전에 `Turn.index`로 찾고, 가짜 문장과 잘못된 인덱스를 코드로 나눈다.
6. 인물 전도는 사람 0건이다. `perspective_swap`은 보조 신호로 적고, 탐지 한계와 A/B 호칭 예문을 같이 적는다.
7. 형식 상한은 스키마 값(headline 60, highlights 6, quote 200, summary 800, strengths/cautions 5, ideal 범위 제약 없음)을 표로 두고, 프롬프트 목표(20자 내외, 3~5개, 0~100)와 스키마 하드 실패를 다른 등급으로 적는다.
8. 정성 1/3/5는 리포트용으로 다시 쓴다. 메신저 몰입 앵커는 쓰지 않는다. 항목은 점수 설명의 장면 연결, 양쪽 균형, LOW 유보, 조언의 구체성이다. 평가자는 2인이다.
9. 골드셋은 언어 품질과 코드 동작, 왕복 단위, `null`+LOW, 빈 대화록, 실패 fixture, 분할을 포함한 뒤에 게이트 숫자를 확정한다.
