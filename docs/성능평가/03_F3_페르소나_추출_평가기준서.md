## 1. 프롬프트 요구사항 분석

### 1.1 입출력 형식
* **입력**: 온보딩 대화록(건너뛰기/조기종료에 따라 **3~10턴 가변**) 및 사용자가 직접 답한 차원 목록(`# 사용자가 직접 답한 항목`).
* **출력 형식**: 단일 JSON 객체 (설명·마크다운·코드펜스 금지).
  ```json
  {
    "avoidance": 78,
    "interests": ["러닝"],
    "routine": ["토요일 아침 조깅"],
    "date_prefer": ["산책"],
    "date_avoid": ["시끄러운 술집"],
    "narrative": {
      "headline": "...",
      "body": "...",
      "traits": ["...", "..."]
    },
    "summaries": [
      {"category": "intimacy", "title": "...", "content": "..."}
    ]
  }
  ```

### 1.2 점수 산정 및 키 생략 원칙 (핵심)
1. **0~100 정수**: 대화에서 명확한 근거가 있을 때만 양 끝(0 또는 100)으로 이동.
2. **미답변 차원 키 생략 (치명 C4)**:
   - 50점은 중간값이 아니라 근거 부족 시 기본값이므로, **명확한 근거가 없는 차원은 50점으로 채우지 말고 키 자체를 반드시 생략**해야 함.
   - `# 사용자가 직접 답한 항목` 목록에 없는 차원은 추측해서 채우지 말 것.
3. **모델 점수 vs 제품 점수 분리**:
   - **모델 점수**: 모델이 생성한 raw JSON에서 미답변 차원 키가 완전히 생략되었는지를 평가.
   - **제품 점수**: 서비스 후처리 코드([`service.py`](file:///Users/hrun/Documents/ktb4-17/KTB-17DEV/app/features/persona/service.py))가 미답변 차원을 `null`로 사후 정리한 DB 저장본 상태를 평가. (제품 점수만 보면 모델의 C4 날조가 은폐되므로 반드시 분리 집계)

### 1.3 서술 (Narrative) 요구사항
* **`headline`**: 프롬프트 40자 이내 (Pydantic 스키마 상한 60자), "○○하지만 ○○한 관계를 원하는 타입" 꼴.
* **`body`**: 3~5문장. **문장마다 사용자가 대화에서 실제로 한 말 하나를 인용/반영**.
  * 톤: "~하는 편이에요" 존댓말. 주어 생략 (당신/닉네임 호칭 금지). 점수 숫자 직접 언급 금지.
  * **짐작/추측 어미 절대 금지**: "~할 것 같아요", "~하실 수 있겠네요", "~일 수도 있어요", "~듯해요" 사용 불가.
* **`traits`**: 특징 3~5개, 각 30자 이내. 사용자가 한 말에서만 도출.
* **금지 표현**:
  * 유형명 금지: "회피형", "불안형" 등 단어 금지.
  * 평가/조언 금지: "좋은 분이시네요", "고치면 좋겠다" 금지.
  * 대화체 반응 금지: 사용자에게 직접 말을 건네는 "~시군요", "~하셨네요" 금지.
  * **프롬프트 복창 금지 (치명 C6)**: 시스템 지시문이나 사용자 입력을 20자 이상 연속 복창 금지.

### 1.4 요약 카드 (`summaries`) 요구사항
* 5개 area(`intimacy`, `communication`, `conflict`, `ideal`, `orientation`)별 최대 1장.
* `title`: 프롬프트 20자 이내 (스키마 40자), "○○ 편" 꼴.
* `content`: 프롬프트 40자 이내 (스키마 200자), "~해요" 톤 한 문장.
* 해당 area에 속한 차원 전부에 근거가 없으면 카드를 완전히 생략.

## 2. 기존 데이터셋 검토 및 쟁점 분석

### 2.1 기존 데이터셋 현황
- 파일: [`persona_build.jsonl`](file:///Users/hrun/Documents/ktb4-17/KTB-17DEV/evals/quality_datasets/persona_build.jsonl) (60건)
- 구성: calibration 12건, regression 36건, blind_holdout 12건.
- 구분: 30건 `label_accuracy` (성향/서술 추출), 30건 `code_behavior` (서비스 후처리 및 결측치 정리).

### 2.2 발견된 결함 및 보완 조치
1. **보강 턴 (`supplement`) 15건 신규 골드셋 구축**:
   - 15개 성향 차원별로 보강 질문과 단답이 1개 추가된 대화록 fixture 15건 신규 설계.
   - 보강 평가 시 LLM이 대화 전체를 다시 추출하므로 기존 점수의 미세 변동이 발생할 수 있음 → **보강 대상 차원은 범위 내 갱신, 나머지 차원은 허용 오차(±5점 이내) 유지**를 오라클로 설정.
2. **폴백 게이트 모순 교정**:
   - 최초 `build`는 실패 시 규칙 초안 폴백(`allow_fallback=True`)이 의도된 정상 안전망임. 따라서 폴백을 C-code 치명(0건)으로 두지 않고, 00 가이드라인에 따라 **모델 점수 실패율(5% 이하)로 분리 집계**.
3. **가드레일 모드 명시**:
   - `extract`는 `mode=enforce`일 때 narrative에 가드레일 위반이 있으면 서술 전체를 `None`/`[]`로 치환함. 결과표에 `GUARDRAIL_MODE` 명시 필수.

## 4. 기존 데이터셋 정비 및 모수 분할

### 4.1 회귀 게이트 유효 모수 (18건)
- 전체 60건 중:
  * 서비스 후처리 `code_behavior` 30건: 모델 평가 분모에서 완전 제외.
  * `blind_holdout` 12건 중 언어 6건: 홀드아웃 분리.
  * `calibration` 12건 중 언어 6건: 사람-Judge 보정용.
  * **`regression` 언어 품질 = 18건** (배포 게이트 실제 유효 모수).

### 4.2 자동 검증 오라클 (`autoMetrics`)
* `unknownScores`: 근거 없는 차원의 점수 키가 모델 raw JSON에서 완전히 생략되었는가 (100% 필수).
* `textualKept` / `textualDropped`: 실제 사용자가 말한 관심사/일과만 텍스트 배열에 유지되었는가.
* `acceptableRanges`: 추출된 점수가 사전 정의된 허용 범위 내에 존재하는가.
