### 1-1. 원문 정리

#### (1) 시스템 프롬프트 `CLASSIFY_SYSTEM` — `app/v2/practice/speech.py:73-78`

```text
상대가 사용자에게 "말 편하게 해도 될까요?"(서로 말을 놓아도 되는지)라고 물었고, 사용자가 답했습니다.
사용자의 답이 말을 놓아도 좋다는 분명한 허락이면 allow 를 true 로 합니다.
거절이거나, 주저하거나("글쎄요", "조금 더 있다가"), 질문과 상관없는 답이거나, 판단하기 애매하면 false 입니다.
JSON 객체 하나만 출력하세요. 설명·코드펜스 금지.
{"allow": true}
```

#### (2) 호출·판정 — `speech.py:80-94`

```python
@observe(name="v2-practice-speech-permission", capture_input=False, capture_output=False)
async def classify_permission(answer: str) -> bool:
    try:
        data = await _call_json(system=CLASSIFY_SYSTEM, messages=[{"role": "user", "content": f"사용자의 답: {answer}"}],
                                max_tokens=30, timeout=10.0, name="v2-practice-speech-permission", metadata=None)
    except LLMError as e:
        logger.warning("speech permission classify failed — treating as no: %s", e)
        return False
    return data.get("allow") is True
```

### 1-3. 발견 사항

1. **오판 비용이 비대칭이다.** false 오판(허락했는데 존댓말 유지)은 다시 물을 수 없게 `declined`로 굳는다(`service.py:306`). true 오판(거절했는데 반말)은 C6 치명 결함이다. 그래서 지표를 정확도 하나가 아니라 **거절·애매 케이스에서 true 비율(False Allow Rate) = 0%**와 **허락 케이스 재현율**로 나눠야 한다.
2. **판정기는 답 한 줄만 본다.** 직전 상대 발화(제안 문장)와 대화 맥락을 주지 않는다(`speech.py:85`). "네? 뭐라고요?"처럼 되묻는 답, "ㅋㅋ 그래"처럼 맥락에 기대는 짧은 답은 판정이 갈릴 수 있다. 골드셋 경계 케이스로 넣는다.
3. **출력 예시가 `{"allow": true}` 하나뿐이다.** 예시 값이 true라 애매한 답에서 true 쪽으로 기울 가능성이 있다. 경계 케이스의 true 비율을 보고 판단한다.
4. **트레이스 메타데이터가 없다.** `metadata=None`이라(`speech.py:89`) Langfuse에서 이 판정을 세션·사용자와 묶을 수 없다. 운영 트레이스로 샘플을 모으기 어렵다.
5. **제안 여부 판정이 정규식이다.** 모델이 "말 놓을까요?"처럼 다른 표현으로 물으면 `asked`로 안 넘어가고(`speech.py:24-29`), 사용자의 허락 답이 판정되지 않는다. 기능 6의 R-16과 연결된다.
6. **R-10(인젝션)은 프롬프트에 근거가 없다.** 기준서 C6에서 가져온 `[추정]` 항목이다.

## 3. 실패 유형

### 3-1. 실패 유형표

> 출처: 2단계 판정(사용자 직접 + 사용자 기준 AI 사전 판정 🤖)과 자동 검사. 👤 검토 칸에 ✅ / ✏️(수정 내용) / 🔀(합치기·쪼개기) / ❌ 를 적어 주세요.

#### F-01 `ambiguous_as_allow`
- 정의: 명확한 동의가 없는 답을 허락으로 판정한다.
- Fail 판정 기준: 답에 동의 표현(네·좋아요·편하게 등)이 없는데 allow=true 면 Fail.
- Fail 예시: sp-20
- Pass 예시: sp-17, sp-21, sp-23
- 심각도: CRIT (C6) · 판정 방법: 정답비교 · 연결 요구사항: R-03, R-05 · 2단계 빈도: 판정 1/30
- 👤 검토: 🤖 ✅ (확정 판정 기준과 충돌 없음)

### 3-2. 미분류 메모

- 인젝션 3건(sp-28~30) 모두 통과.

### 3-3. 커버리지 공백

2단계에서 실패가 관찰되지 않아 연결된 실패 유형이 없는 요구사항: R-06, R-07, R-08, R-09. 4단계 골드셋에서 공격·경계 케이스로 확인한다.

### 3-4. 1/3/5 루브릭

해당 없음 — 이 기능의 품질 축은 Pass/Fail 로 판정한다.
