1.한눈에 보기

소개팅 AI 서버는 AI가 하는 일이 세 가지입니다. ① 온보딩(사용자에게 질문하고 답에서 성향을 뽑아 페르소나 만들기), ② 연습대화(다른 사람 역할을 맡은 AI와 대화), ③ 시뮬레이션(두 사람의 가상 대화와 궁합 리포트). 이 문서는 그 세 가지를 같은 문제로 반복해서 채점하려고 만든 시험 문제집(합성 테스트셋)을 설명합니다. 세 가지를 더 잘게 나눠 문제집을 5종으로 만들었습니다(아래 표).

용어 풀이

  • 케이스: 문제 1개. Dataset: 기능별로 묶은 문제 묶음.
  • 합성 데이터: 실제 사용자 대화가 아니라 코드와 기획서를 바탕으로 만든 가상 문제입니다(개인정보 없음).
  • calibration(보정용): 채점 기준이 납득되는지 사람이 맞춰 보는 문제. 프롬프트를 고칠 때 봐도 됩니다.
  • regression(회귀 검사용): 프롬프트를 바꿀 때마다 돌려서 이전보다 나빠지지 않았는지 확인하는 문제.
  • blind_holdout(최종 확인용): 프롬프트를 고칠 때 보지 않고 마지막에 확인하는 문제. 다만 파일이 그대로 공개돼 있어 진짜 비밀은 아닙니다.

  • 카테고리·난이도: 문제의 종류(예: 짧은 답변, 정체 질문)와 어려운 정도.

2.왜 만들었나

프롬프트나 모델을 바꿀 때마다 “좋아졌나?”를 감으로 판단하면 회귀를 놓칩니다. 같은 입력 묶음으로 전후를 비교하려고 고정된 테스트셋이 필요했고, 기능마다 실패 경계가 달라서 Dataset을 나눴습니다. 기획서 docs/v1docs/langfuse-quality-dataset-plan.md의 핵심은 다음과 같습니다.

Dataset 분리 원칙

하나의 통합 Dataset에 넣지 않고 generation 이름과 실패 경계에 맞춰 분리합니다. 발화는 좋아졌지만 태깅이 나빠진 경우처럼 원인을 나눠 볼 수 있기 때문입니다.

기획서의 설계 원칙

  • 3.1 기능별 Dataset을 분리한다
  • 3.2 문자열 정답보다 평가 가능한 계약을 저장한다
  • 3.3 규칙 오라클, 사람 평가, LLM Judge를 분리한다
  • 3.4 폴백을 품질 성공으로 세지 않는다
  • 3.5 테스트 데이터와 운영 개인정보를 분리한다

제품 기준값과 초기 제안값

기획서는 수치를 두 종류로 구분합니다. 뒤쪽은 데이터가 쌓인 뒤 보정할 값이며 처음부터 영구 합격선이 아닙니다.

  • 제품 기준값: 현재 코드에 이미 정의된 턴 수, 점수 공식, 길이, 토큰 상한, 타임아웃이다.
  • 초기 운영 제안값: 품질 점수와 회귀 허용 범위처럼 데이터가 쌓인 뒤 보정해야 하는 값이다. 처음부터 영구적인 합격선으로 간주하지 않는다.

기획서의 권장 분할은 calibration 20%, regression 60%, blind_holdout 20% 입니다. 같은 원형에서 파생된 항목은 모두 같은 split에 둡니다.

3.케이스 한 건의 구조

각 줄(케이스)은 input, expectedOutput, metadata 세 덩어리입니다. expectedOutput은 정답 문장이 아니라 채점 기준입니다. 생성형 답변은 정답이 여러 개라서, 반드시 지킬 계약(hardAssertions), 하면 안 되는 것(forbidden), 1/3/5점 루브릭, 기능별 세부 contract를 저장합니다.

input

모델(또는 평가 어댑터)에 주는 상황. 일부 필드(candidateOutput, faultInjection 등)는 모델에 넣는 힌트가 아니라 어댑터용 fixture입니다.

expectedOutput

채점 기준. 점수도 단일 정답이 아니라 acceptableRanges(검토 대기 범위)로 둡니다.

metadata

caseId, category, difficulty, familyId, split, sourceRefs(근거 코드 위치), reviewFlags 등.

아래는 Dataset별 실제 케이스 한 건(regression 분할의 첫 케이스)을 줄여 보인 것입니다. 긴 값은 90자에서 자르고, 원본 전체는 review 문서에서 볼 수 있습니다.

7.앱 코드가 바뀌면 테스트셋도 바뀌는 이유

이 데이터셋의 기대값(특히 규칙 점수·총점·등급·토큰 상한)은 앱 코드에서 계산한 값입니다. 그래서 앱 동작이 바뀌면 케이스 자체가 아니라 기대값이 낡습니다. manifest에 근거 소스의 해시를 기록하는 것도, 앱 순수 함수로 기대값을 재계산하는 드리프트 테스트(tests/test_quality_datasets_drift.py)를 두는 것도 이 때문입니다.

기준이 된 앱 커밋은 f7cc806이고, 그 뒤 바뀐 동작은 다음과 같이 반영되었습니다 (revision_v1_4_report.md 발췌).

  • 근거 없는 점수는 50이 아니라 null(모름)이다. DEFAULT_SCORE 삭제, 저장된 옛 행의 "신뢰도 LOW인 50"은 known_scores가 null로 읽는다. 궁합 계산은 모름 차원의 규칙 점수를 null로 두고 영역 평균과 위험 판정에서 뺀다. 단 dimensions[].a/b 표시값은 백엔드 계약(#63) 때문에 모름이어도 50이다.
  • 페르소나 입력의 빈 차원: 50 → null (complete_persona).
  • ruleOracle: 규칙 차원 점수·영역 점수·위험·총점을 null 기준으로 재계산했고, 표시값은 dimensionDisplay로 분리했다.
  • persona_build: postService.defaultScores(50) → unknownScores(null). 서비스는 답변에서 근거가 확인된(answered) 차원만 값을 남긴다. forbidden에 "직접 답하지 않은 차원을 다른 답에서 미루어 채움"을 추가했다.
  • raw_null 후처리 검사: contactRhythm 50 → null. preview의 missingDimensionInputDefault: 50은 missingDimensionScore: null과 missingDimensionDisplay: 50으로 나눴다.
  • 시뮬레이션 실행 계약. max_tokens = 3000 + 300 × turns(예전 2200 + 180 × turns). 깨지거나 잘린 출력은 남은 시간이 총 timeout의 1/3을 넘으면 1회 재시도하므로 runtime.maxLlmCalls = 2. 계속 깨지는 invalid_json fault는 두 번 호출 후 실패하므로 llmCalls = 2이고 retryCondition을 기록했다. timeout은 재시도하지 않는다.

현재 앱 코드와 품질 계약의 차이 (README)

평가용 반례로 기록된 것이며 앱 코드는 고치지 않았습니다.

  • next_topic은 정상 후보가 모두 소진되면 마지막 두 턴의 HEAVY 금지를 완화한다.
  • build headline은 프롬프트 40자와 schema 60자, summary title/content는 20/40자와 40/200자로 다르다.

  • ReportNarrative의 ideal_fit은 현재 값의 0~100 범위 제약이 없다.
  • 위험 caution을 뒤에 붙인 후 [:5]로 자르므로 기존 caution 5개가 있으면 위험 문장이 유실될 수 있다.

9.직접 검토하는 방법

사람 라벨이 아직 없으므로, 팀원이 직접 읽고 판정하는 것이 다음 신뢰 확보 단계입니다. 검토용 문서는 evals/review/quality_dataset_review.html 하나이며 브라우저로 열면 됩니다(서버 불필요).

  1. 상단 탭에서 Dataset을 고르고, 분할 버튼(calibration/regression/blind_holdout)과 검색창으로 케이스를 좁힙니다.
  2. 케이스를 펼쳐 입력, 반드시 지킬 것, 하면 안 되는 것, 채점 기준을 읽습니다.
  3. 판정 버튼으로 적절, 수정 필요, 부적절 중 하나를 고르고, 이유·수정 제안을 메모합니다.
  4. 판정은 이 브라우저의 localStorage에만 저장됩니다. 공유하려면 검토 결과 내보내기(JSON)로 dataset-review.json를 받아 전달합니다.

검토 순서 제안

  1. calibration부터: 루브릭 문장이 채점 가능한지, 기준을 팀이 같이 맞춥니다.
  2. 검토 보고서가 지적한 High 항목의 케이스를 우선 봅니다(위 검토 이력 참고).
  3. Dataset마다 무작위 몇 건을 골라 입력에 정답 힌트가 섞이지 않았는지, 허용 범위가 과하게 좁거나 넓지 않은지 봅니다.
  4. 마지막에 blind_holdout을 봅니다. 프롬프트를 고치는 사람은 holdout을 보지 않는 것이 원칙입니다.
  5. 같은 케이스를 두 사람이 독립적으로 판정하고 불일치만 토론합니다(이중 라벨의 예행연습).

10.다음 단계

신규 케이스 후보

앱 프롬프트가 바뀌었지만 이를 검사하는 케이스가 아직 없는 영역입니다. 추가하면 케이스 수와 분할이 바뀌므로 별도 결정이 필요합니다.

  • 온보딩·연습대화의 “저번에/지난번에” 금지와 기억은 대화에 실제로 있던 것만 쓰기
  • 시뮬레이션 화자 분리(두 사람의 특성·호칭이 뒤섞이지 않기)와 재시도 경로
  • 범위 밖 요청(직업·나이 직접 질문, 조언 유도, 농담·욕설)
  • MBTI 말투 힌트 분기

신뢰도를 올리는 순서

  1. 사람 이중 라벨: 두 사람이 독립 라벨링하고 조정해 의미 라벨과 허용 범위를 확정
  2. Judge calibration: 사람 앵커와의 일치도를 확인한 뒤에만 LLM Judge 점수를 사용
  3. 실제 모델 baseline 실행: 평가 어댑터를 만들고 현재 프롬프트·모델의 품질, 지연, 비용 기준선을 측정
  4. 새 원형으로 만든 봉인된 holdout 준비

최근 수정 보고서가 남긴 미해결 항목

  • 신규 케이스 중 "저번에/지난번에" 금지(온보딩 발화·연습대화), 시뮬레이션 화자 분리 재시도·truncated·upstream_error fault, MBTI 말투 힌트는 추가하지 않았다. 필요한 fault 주입 구조를 시뮬레이션 생성기에 새로 만들어야 해서 별도 작업으로 남겼다.
