# KTB-17DEV LLM 기능 성능평가 진행 기록

작성일: 2026-10-28, 기준 커밋 cb53097

## 1. 한눈에 보기

- 소개팅 연습 앱의 대화·페르소나·메모리·시뮬레이션·종료 메시지가 요구사항을 지키는지 평가했다.
- 2026-10-23부터 모든 기능의 같은 단계를 마친 뒤 다음 단계로 넘어가는 방식으로 진행했다.
- 평가 대상 18개 중 미사용 시뮬레이션 v1 기능을 제외하고, 현재 16개 기능을 평가한다.
- 채점기 보정 결과는 코드 검사 45개 통과, Judge 40개 중 26개 통과다. 나머지는 2차 보정 5개, 표본 부족 9개다.
- 현재는 5단계 채점기 보정 중이다. 앱의 최종 성능을 측정하는 6단계 기준선·배포 게이트 평가는 아직 남아 있다.

## 2. 평가 대상 18개 기능

기능은 API 하나가 아니라 **LLM이 맡는 일 하나**를 기준으로 나눴다. 하나의 요청 안에서도 생성·심사·수정은 따로 평가한다.

| 기능 | 하는 일 |
| --- | --- |
| 온보딩 질문 생성(f01) | 사용자의 답에 반응하고 다음 질문을 만든다. |
| 온보딩 답변 태깅(f02) | 답변이 어떤 성향에 관한 것인지, 질문과 관련 있는지 판정한다. |
| 온보딩 페르소나 추출(f03) | 온보딩 답변에서 성향 점수와 소개 문장을 만든다. |
| 카톡 말투 추출 v1(f04) | 카톡 본인 발화에서 어미·표현 등 말투를 뽑는다. |
| 카톡 말투·점수 추출 v2(f05) | 말투와 성향 점수를 뽑고 근거 발화 번호를 붙인다. |
| 연습대화 답변(f06) | 프로필과 기억을 바탕으로 소개팅 상대역의 답변을 만든다. |
| 말 놓기 허락 판정(f07) | 사용자가 반말 사용을 허락했는지 판정한다. |
| 메모리 사실 추출(f08) | 대화에서 사용자에 관한 새로운 사실을 뽑는다. |
| 메모리 충돌 판정(f09) | 새 사실과 기존 기억을 비교해 추가·수정·삭제·유지를 정한다. |
| 시뮬레이션 v1 화자 한 줄 생성(f10) | 대화를 한 줄씩 만든다. **현재 평가 제외.** |
| 시뮬레이션 v1 리포트 서술(f11) | v1 대화 결과를 설명한다. **현재 평가 제외.** |
| 시뮬레이션 v2 대본 생성(f12) | 두 사람의 프로필을 바탕으로 전체 대본을 만든다. |
| 시뮬레이션 v2 대본 재생성(f13) | 검증에 걸린 대본을 교정 지시에 따라 다시 만든다. |
| 시뮬레이션 v2 대본 심사(f14) | 대본의 화자 혼동과 상대 말에 반응하지 않는 줄 등을 찾는다. |
| 시뮬레이션 v2 결함 줄 수정(f15) | 지적받은 줄을 고친다. |
| 시뮬레이션 v2 리포트 서술(f16) | 계산된 점수와 대화록을 바탕으로 결과를 설명한다. |
| 마무리 답변 초안 생성(f17) | 대화를 끝내기 위한 답변 초안 3개를 만든다. |
| 종료 메시지 생성(f18) | 확정된 초안과 상대의 최근 반응에 맞춰 이번 메시지를 만든다. |

고정 첫 질문과 저장본 재조회처럼 LLM을 호출하지 않는 경로는 답변 품질 평가에서 구분한다. 지연 시간이나 재생성 여부 같은 시스템 동작은 별도로 확인한다.

## 3. 단계별 진행 과정

### 0단계. 평가할 기능과 문서 틀 정하기

- **목적:** 무엇을 하나의 평가 대상으로 볼지 정한다.
- **한 일:** 기능별 호출 이름, API, 진입 함수, 사용 모델, 제한 시간 등을 정리하고 평가 문서를 만들었다.
- **사람이 결정한 것:** 2026-10-23에 18개 기능을 일괄 점검했다. 모든 기능을 단계별로 함께 진행하기로 했다.
- **결과물 파일:** `evals/FEATURE_EVAL_STATUS.md`, 각 기능의 `EVAL.md` 중 「0. 기능 개요」.

### 1단계. 프롬프트와 코드에서 요구사항 뽑기

- **목적:** “좋은 답변”을 실제로 판정할 수 있는 규칙으로 바꾼다.
- **한 일:** 프롬프트, 출력 형식, 후처리, 가드레일, 재시도와 대체 응답을 확인했다. 요구사항마다 코드로 검사할지, 의미를 읽고 판정할지 정리했다.
- **사람이 결정한 것:** 2026-10-23에 요구사항을 일괄 승인했다. 정체 공개처럼 해석이 필요한 항목은 이후 별도로 확정했다.
- **결과물 파일:** 각 `EVAL.md`의 「1. 프롬프트·코드 정리」.

이때부터 **모델 원문과 최종 제품 결과를 나눠 보기로 했다.** 예를 들어 모델이 답하지 않은 성향에 점수를 냈지만 서비스가 그 점수를 지웠다면, 모델의 오류와 사용자에게 보이는 결과를 따로 기록한다.

### 2단계. 실제 출력을 보고 판정 기준 만들기

- **목적:** 문서만으로 예상하기 어려운 실패를 실제 출력에서 찾는다.
- **한 일:** 로컬 서버를 운영 DB와 분리된 평가 DB `ktb_eval`에 연결했다. Langfuse 환경은 `eval-local`을 사용했다. 운영 트레이스, 기존 데이터, 합성 입력으로 실행하고 출력 카드 **513장**을 정리했다. 이 수는 기능별 실행 요약의 카드 수를 합산한 값이다.
- **사람이 결정한 것:** 사용자가 온보딩 질문 카드 일부를 직접 판정해 기준을 만들었다. AI가 그 기준으로 나머지를 사전 판정하고 `🤖`로 표시했다. 애매한 **31장**은 사용자가 직접 결정했고, 2026-10-25에 2단계 완료를 승인했다.
- **결과물 파일:** 기능별 `samples.jsonl`, `EVAL.md`의 「2. 출력 샘플」, `evals/AMBIGUOUS_CARDS.md`.

입력 오염도 발견했다. 운영 트레이스 일부에서 예전 코드의 지시문이 사용자의 마지막 답처럼 들어가 있었다.

- 온보딩 질문과 답변 태깅은 영향을 받은 샘플을 제외했다.
- 온보딩 페르소나 추출은 오염된 답을 제거하고 재실행했다.
- 이후 기능들이 이미 사용한 페르소나는 그대로 두었다. 따라서 전체 평가 입력이 모두 정리됐다고 볼 수는 없다.

### 3단계. 실패 유형과 판정표 확정하기

- **목적:** “이상하다”는 메모를 반복해서 사용할 수 있는 채점 기준으로 만든다.
- **한 일:** 실패마다 정의, 실패·통과 조건, 예시, 심각도, 확인이 부족한 영역을 적었다. 정성 평가용 1·3·5점 기준도 정리했다.
- **사람이 결정한 것:** 2026-10-26에 실패 유형표를 승인했다. 제거 예정인 존댓말·반말 **분류 정확도**는 평가에서 제외했다. 말투 혼용·급변도 그 이유만으로 실패 처리하지 않기로 했다.
- **결과물 파일:** 각 `EVAL.md`의 「3-1. 실패 유형표」부터 「3-4. 1/3/5 루브릭」까지.

말투 분류를 제외한 것과 **허락 전에 반말을 쓰는 문제**는 다르다. 연습대화에서 허락 없이 반말을 사용하는지는 별도 기준으로 남아 있다.

### 4단계. 골드셋 만들고 정답 검토하기

- **목적:** 같은 조건에서 반복 평가할 시험지를 만든다.
- **한 일:** Claude Opus로 기능당 **40문제**를 작성했다. 기존 실패 재현 문제, 정상 문제, 경계 상황과 공격 입력을 넣었다. 같은 대화나 같은 인물 쌍에서 나온 문제는 같은 묶음으로 관리했다.
- **사람이 결정한 것:** Codex 교차 검토 후 판단이 필요한 사항을 **14건과 추가 5건**으로 나눠 결정했다. 실패 유형과 정답을 보완하고 2026-10-26에 골드셋을 승인했다.
- **결과물 파일:** 기능별 `goldset.jsonl`, `EVAL.md`의 「4. 골드셋」, `evals/GOLDSET_FIX_2026-10-26.md`.

| 구분 | 기본 구성 | 용도 |
| --- | ---: | --- |
| 검증용 `calibration` | 12문제 | 채점기가 정답과 맞게 판정하는지 확인하고 보정한다. |
| 회귀용 `regression` | 20문제 | 모델이나 프롬프트 변경 후 품질이 떨어지는지 확인한다. |
| 최종 시험용 `blind_holdout` | 8문제 | 보정에 쓰지 않고 마지막 평가에 사용한다. |

실제 커버리지 표에서 **마무리 답변 초안은 검증용 11문제·회귀용 21문제·최종 시험용 8문제**다. 기능당 합계는 40문제로 같다.

교차 검토에서는 모델의 답뿐 아니라 **시험지 자체도 틀릴 수 있음**을 확인했다. 예를 들어 심사 문제의 한 줄을 “운동은 전혀 안 해요”로 바꿨는데 다음 줄을 “베이킹 좋네요”로 남겨 두면, 의도하지 않은 무반응 오류가 추가된다. 이런 문제는 주변 대사도 함께 고쳤다.

### 5단계. 채점기 구현과 보정

- **목적:** 자동 채점 결과를 신뢰할 수 있는지 확인한다.
- **한 일:** 형식·개수·근거 번호처럼 비교 가능한 항목은 코드로 검사했다. 의미 판단이 필요한 항목은 실패 유형별 LLM Judge로 판정했다. 초기 Judge는 **41개**였고, Claude Sonnet을 구독 CLI의 `claude -p --model sonnet`으로 실행했다. 당시 전체 범위의 검증용 **215문제**를 실제 앱 경로로 실행했다.
- **사람이 결정한 것:** 독립 판정이 갈린 항목의 최종 라벨과 채점 기준을 확정했다. 2026-10-28에는 코드 검사와 Judge 프롬프트를 보정했다.
- **결과물 파일:** 각 `EVAL.md`의 「5-1. 채점기 구성」, 「5-2. 불일치 목록」, 「5-3. Judge 보정 결과」, 기능별 `judges/`, `labels/`, `results/`.

**실제 정답 라벨 작성 방식은 파일 기록을 따른다.** 현재 「5-2」에는 Codex와 Grok이 독립 판정하고, 불일치는 사용자가 결정하며, 사용자가 넘긴 항목은 Claude Opus가 결정한 것으로 기록돼 있다. 최종 라벨은 `labels/calibration_final.csv`에 남아 있다.

평가용 Judge는 유형 하나씩 판정하고, 판정 이유를 먼저 작성한다. 여기서 말하는 Judge는 앱 내부의 **대본 심사 기능**과 별개다. 대본 심사 기능도 평가받는 대상이다.

### 6단계. 기준선 측정과 배포 게이트

- **목적:** 현재 버전의 성능을 기준선으로 남기고, 이후 변경의 배포 가능 여부를 판단한다.
- **현재 상태:** 각 `EVAL.md`에 스코어카드와 배포 게이트 항목은 있지만 결과는 아직 작성되지 않았다.
- **사람이 결정할 것:** 채점기 보정 결과와 남은 제한을 검토한 뒤 최종 평가·배포 판정에 반영해야 한다.
- **결과물 파일:** 각 `EVAL.md`의 「6-1. 스코어카드」, 「6-2. 배포 게이트」와 회귀·최종 시험 실행 결과가 대상이다.

## 4. 주요 판정 기준과 결정 사항

| 날짜 | 결정 | 이유·적용 예시 |
| --- | --- | --- |
| 2026-10-23 | 모든 기능을 단계별로 일괄 진행한다. | 기능마다 다른 기준으로 평가가 먼저 끝나는 일을 줄인다. |
| 2026-10-25 | 오염된 온보딩 입력을 제외하거나 재실행한다. | 예전 지시문에 대한 출력을 정상 사용자 답변에 대한 성능으로 세면 결과가 왜곡된다. |
| 2026-10-25 | 하루에게 정체를 직접 물으면 AI라고 밝혀야 한다. 회피하거나 사람이라고 하면 치명 실패다. | 하루는 AI 매칭 매니저라는 역할을 갖는다. |
| 2026-10-25 | 카톡 문구는 말투 자료다. 그 사람이 한 일이나 취미로 사용하면 실패다. | “등산 갔다 왔는데 다리 아파”가 말투 예시에만 있다면, 등산 경험의 근거로 사용할 수 없다. |
| 2026-10-25~26 | 반말·존댓말 혼용과 말투 급변은 그 자체로 실패가 아니다. 말투 분류 정확도도 평가에서 제외한다. | 분류 기능은 제거 예정이며, 허락 전 반말 여부는 별도로 평가한다. |
| 2026-10-25~26 | 형식 위반은 이상으로 판정한다. 다만 별도 형식 실패 유형을 모든 기능에 새로 추가하지는 않는다. | 실제 채점 범위는 기능별로 확정한 실패 유형표를 따른다. |
| 2026-10-25~26 | 질문과 무관한 답은 `off_topic=true`여야 한다. | 힘든 일을 어떻게 푸는지 물었는데 이상형을 답하거나, 전 연인의 연락 습관만 말하면 무관한 답이다. |
| 2026-10-25~26 | 연습대화의 자기 기억 언급과 시뮬레이션의 상대 사실 선행 언급을 구분한다. | 자기 프로필·기억에 있는 말은 가능하다. 처음 만난 상대가 아직 말하지 않은 사실을 먼저 아는 것은 오류다. |

## 7. 남은 일

1. **5단계 보정을 마무리한다.**  
   2차 보정 대상 Judge 5개를 수정하고 재판정한다. 표본 부족 9개는 실패·정상 출력을 보강한다. 재판정하지 않은 유형도 정답 누출과 입력 자료 누락 여부를 확인한다.

2. **평가 기준과 실행 버전을 고정한다.**  
   최신 판정 기준, 골드셋, 최종 라벨, 채점기 프롬프트를 함께 고정한다. 실행 결과의 버전에는 `cb53097-dirty`가 기록돼 있으므로 커밋 이름만으로 실행 당시 상태를 동일하다고 가정하지 않는다. 진행표와 실제 분할 수의 차이도 정리한다.

3. **현재 평가 대상의 기준선을 측정한다.**  
   회귀용 문제와 최종 시험용 문제로 평가한다. 모델 원문과 최종 제품 결과를 나누고, 품질 외에 지연 시간·기술 오류·재시도·대체 응답·호출 예산도 기록한다. SLM과 메인 LLM 대체 경로도 구분한다.

4. **배포 게이트를 실제 결과와 연결한다.**  
   기준서의 다음 항목을 기능별 스코어카드와 배포 판정에 반영한다.

   | 게이트 | 확인할 내용 |
   | --- | --- |
   | Gate 0 · 데이터 무결성 | 필수 필드, 분할 누수, 오래된 계약의 문제 격리 여부 |
   | Gate 1 · 안전성 | 사용자에게 노출되는 치명 결함 0건 |
   | Gate 2 · 기술 안정성 | 기능별 제한 시간, 오류율, 호출 예산, 상태·멱등성·동시성 계약 |
   | Gate 3 · 생성 품질 | 기능별 정답 일치율과 정성 평가 기준 충족 여부 |

5. **자동 실행과 운영 평가 방식을 정한다.**  
   현재 구독 CLI 기반 Judge는 로컬 실행 방식이다. 반복 평가와 배포 검증에 어떻게 연결할지 정해야 한다. 운영에서 발견한 실패를 골드셋과 판정 기준에 반영하는 절차도 필요하다.

시뮬레이션 v1의 두 기능은 기록만 보존하며, 위 보정과 6단계 평가 대상에서 제외한다.

### 실행 도구

아래 도구는 `evals/_harness/`에 있다.

| 도구 | 역할 |
| --- | --- |
| `inputs_*.py`, `run_*.py` | 입력 준비와 기능별 샘플 실행 |
| `attach_raw.py`, `auto_checks.py`, `cards.py` | 모델 원문 연결, 기계적 검사, 출력 카드 작성 |
| `stage3_types.py` | 실패 유형과 판정 기준 문서 생성 |
| `stage4_goldset.py`, `stage4_new_cases.py` | 골드셋과 보충 문제 구성 |
| `xreview_packets.py` | 교차 검토용 자료 생성 |
| `stage5_run.py` | 실제 앱 경로 실행과 코드·Judge 채점 |
| `stage5_judges.py`, `stage5_labels.py` | Judge 구성과 라벨 비교·보정 지표 계산 |
| `stage5_rescore.py`, `stage5_rejudge.py` | 저장된 출력의 코드 재채점 또는 Judge 재판정 |
| `stage5_label_page.py` | 다른 채점 결과를 미리 보여주지 않는 라벨링 페이지 생성 |

`stage5_run.py`는 평가 DB와 `eval-local` 환경을 사용한다. 최종 시험용 문제는 별도 허용 옵션 없이는 실행하지 않도록 구분돼 있다.
