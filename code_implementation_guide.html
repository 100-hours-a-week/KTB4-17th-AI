1

프로젝트 개요 & 시스템 아키텍처

KTB4-17th-AI는 연애 소개팅 매칭 서비스인 '별이삼샵'의 핵심 지능형 백엔드 서버입니다. 단순한 챗봇이 아니라 사용자의 대화로부터 15개 가치관 차원을 실시간 추적하고, 저장된 페르소나들 간의 가상 소개팅 시뮬레이션 및 1:1 실시간 롤플레잉 대화를 고성능 비동기(Async) 구조로 안전하게 처리합니다.

High-Level Architecture & Domain Pipelines

엄격한 레이어드 아키텍처 (Layered Architecture Rules)

프로젝트는 코드베이스의 유지보수성과 테스트 격리를 위해 계층별 책임을 엄격히 제한하고 있습니다.

Pydantic 스키마 검증, 상태 코드 반환, HTTP 에러 매핑만 수행합니다. 비즈니스 로직을 절대 작성하지 않습니다.

어떤 질문을 언제 던질지, 점수를 어떻게 환산할지, 트랜잭션 커밋/롤백 시점을 전적으로 통제합니다.

agents.py
LLM 대화 및 서술 생성

"어떻게 말할 것인가"만을 담당합니다. 프롬프트 엔지니어링, JSON 포맷팅, 토큰 한도 제어, Langfuse 트레이싱을 포함합니다.

repository.py & models.py
데이터 영속성 계층

Service는 SQLAlchemy 쿼리를 직접 작성하지 않고 Repository를 통해서만 안전하게 DB에 접근합니다.

공통 인프라 규약 (app/core/)
  • 단일 공통 Base (app.core.db.Base): 기능별(feature)로 Base를 분리하면 시뮬레이션 및 연습대화가 personas 테이블에 외래키(ForeignKey)를 맺을 때 MetaData 불일치가 발생하므로 모든 모델이 단일 Base를 상속.
  • 비동기 커넥션 풀링 (pool_pre_ping=True): 비동기 asyncpg 풀에서 유실되거나 끊긴 연결을 감지하여 재연결 보장.
  • Pydantic v2 Settings (app.core.config.Settings): OpenRouter API 키 및 로컬 vLLM/Ollama 호환 엔드포인트를 통일된 OpenAI 규격 클라이언트로 추상화.

동적 토픽 선택 알고리즘 (next_topic)

정해진 순서대로 묻지 않고, 이전 대화에서 채워진 차원 커버리지(Coverage)를 계산하여 가장 많은 빈 차원을 채울 수 있는 주제를 동적으로 선정합니다. 

# app/features/persona/service.py: next_topic 발췌
def next_topic(coverage: Coverage, turn_index: int, total_turns: int, used_topic_ids: list[str]) -> Topic | None:
    empty = coverage.empty_dimensions()
    remaining = total_turns - turn_index

    # 1. 마지막 턴(턴 9)은 항상 클로징 주제(orientation)로 고정
    if remaining == 1:
        for t in TOPICS:
            if t.is_closing and t.id not in used_topic_ids:
                return t

    def allowed(t: Topic) -> bool:
        if t.id in used_topic_ids: return False
        if t.is_closing: return False
        # 첫 턴은 부담 없는 아이스브레이킹(Weight.LIGHT)만 허용
        if turn_index == 0 and t.weight != Weight.LIGHT: return False
        # 갈등 등 무거운 질문(HEAVY)은 중반(5턴 이후)부터 허용
        if t.weight == Weight.HEAVY and turn_index < 5: return False
        # 대화 마무리가 어두워지지 않도록 마지막 2턴 전에는 HEAVY 금지
        if t.weight == Weight.HEAVY and remaining <= 2: return False
        return True

    candidates = [t for t in TOPICS if allowed(t)]
    if not candidates:
        # 안전망: 제약 때문에 후보가 비면 규칙을 완화하여 남은 주제 중 가벼운 순으로 선택
        candidates = [t for t in TOPICS if t.id not in used_topic_ids and not t.is_closing]
    if not candidates:
        return None

    # 빈 차원을 가장 많이 채우는 주제 우선(-len), 동점이면 무게가 가벼운 것 우선
    return min(candidates, key=lambda t: (-len(set(t.covers) & empty), int(t.weight)))

3중 에이전트 분리 원칙 (Conversation / Tagging / Extraction)

대화와 가치관 추출을 하나의 LLM 호출로 묶지 않는 것이 프로젝트의 핵심 철학입니다. 한 번에 합치면 모델이 대화하느라 추출을 건너뛰거나, 추출을 신경 쓰느라 말투가 건조해집니다.

ConversationAgent
소개팅 상대 "하루" 발화

공감 멘트와 다음 질문을 자연스럽게 생성. 온보딩 질문 텍스트는 segments로 나누어 클라이언트가 말풍선을 분할 표시할 수 있게 반환.

TaggingAgent
턴별 경량 판정 (Fast)

사용자의 답변이 질문에 맞는지(off_topic) 확인하고, 주 근거(primary)와 부 근거(secondary) 차원을 태깅하여 동적 커버리지 갱신.

ExtractionAgent
대화 전체 → 페르소나 초안

10턴 대화 완료 후 호출. 15대 점수, 4대 텍스트 항목, 한 줄 요약(headline), 본문(body), 핵심 성향(traits)을 포괄 추출.

코드 레벨의 엄격한 근거 필터링 & 모순 검증

LLM이 지시를 어기고 사용자가 답하지 않은 차원을 제멋대로 짐작해 채우는 현상을 방어하기 위해 service.py에서 코드 레벨 검증을 수행합니다. 

# app/features/persona/service.py: build_persona 발췌
answered = await self._dimensions_from_answers(session) # 태깅된 primary 차원들만 수집
raw = await self.extraction.extract(self._history(session), answered=answered)

    if value is not None and key not in answered:
        value = None
    scores[key] = value
    evidence = max(coverage.primary.get(key, 0), 1 if key in answered else 0)
    confidence[key] = confidence_of(value is not None, evidence)

턴 중복 방지 (Idempotency) 및 DB 레벨 격리

클라이언트가 지연 등으로 직전 턴의 답변을 재전송하면 turn_index < session.turn_index 조건을 감지하여 DB를 건드리지 않고 현재 대기 중인 질문을 재반환합니다. 또한 DB 테이블 레벨에서 UniqueConstraint("session_id", "turn_index")를 두어 동시성 요청 발생 시 늦게 도달한 쪽을 안전하게 차단합니다.

3

시뮬레이션 & 매칭 리포트 (app/features/simulation/)

두 사용자의 페르소나를 가상 공간에 대면시켜 10턴(왕복 20줄)의 가상 소개팅 대본을 생성하고 궁합 매칭 리포트를 도출합니다. 특히 "수학적 규칙 점수(No LLM) + LLM 1회 대본·서술 통합 생성"이라는 독창적인 2단계 하이브리드 파이프라인으로 설계되었습니다.

100% 결정론적 규칙 점수 산출식 (report.py)

점수를 LLM에게 맡기면 같은 페르소나라도 호출할 때마다 점수가 바뀌어 사용자 불신을 초래합니다. 시뮬레이션에서는 점수를 100% 결정론적 수식으로 산출합니다. 

# app/features/simulation/report.py: dimension_score
def dimension_score(fit: Fit, a: int, b: int) -> int | None:
    if fit == Fit.SIMILAR:
        # 유사형 (연락 빈도, 거리 두기 등): 차이가 적을수록 만점 (100 - |a - b|)
        return 100 - abs(a - b)
    if fit == Fit.BOTH_HIGH:
        # 다다익선형 (표현력, 긍정성 등): 둘 다 높을수록 높은 점수 ((a + b) // 2)
        return (a + b) // 2
    if fit == Fit.BOTH_LOW:
        # 갈등 부정형 (회피·철수, 감정적 맞대응 등): 둘 다 낮아야 안전 (100 - (a + b) // 2)
        return 100 - (a + b) // 2
    return None  # Fit.JUDGED: 이상형(ideal) 영역은 수치 비교가 불가능하므로 대본을 보고 LLM 판정
Null 처리 규칙: 두 사람 중 한 명이라도 특정 차원이 null(온보딩 미답변)인 경우 임의로 50점을 채우지 않고 score=None으로 처리하여 평균 산출에서 아예 제외합니다. (50점으로 채우면 둘 다 모를 때 SIMILAR 점수가 100점으로 왜곡되는 현상 방지)

위험 조합(Risks) 감지 & 가중치 감점 체계

두 사람의 성향이 결합되었을 때 관계를 파괴할 수 있는 특정 조합(예: 한 쪽 회피 ≥ 65 + 상대방 불안 ≥ 65)을 사전 감지하여 전체 점수에서 페널티를 차감합니다. 

# app/features/simulation/report.py: overall_score 발췌
def overall_score(area_scores: dict[str, int | None], risks: list[Risk]) -> int:
    # 5대 영역 가중치: intimacy(25%), communication(30%), conflict(25%), ideal(10%), orientation(10%)
    weighted = [(s, AREA_WEIGHT[a]) for a, s in area_scores.items() if s is not None]
    if not weighted:
        return 50
    base = sum(s * w for s, w in weighted) / sum(w for _, w in weighted)
    # 감지된 모든 위험 요인의 패널티(penalty)를 합산 차감
    return max(0, min(100, round(base) - sum(r.penalty for r in risks)))

LLM 1회 호출로 대본 + 리포트 동시 생성 (SimulationAgent)

대본 생성과 리포트 서술 작성을 분리하지 않고 단 한 번의 LLM JSON 호출로 처리합니다. 이를 통해 비용과 대기 시간을 절반으로 줄이며, 모델이 자신이 방금 작성한 대화 대본의 특정 구절을 turn_index로 정확하게 인용(Highlight)할 수 있습니다.

대본 정규화 엔진 (normalize_script)

LLM이 간혹 같은 화자의 대사를 연속으로 내보내거나 순서를 바꾸는 문제를 방어하는 후처리 로직입니다. 

# app/features/simulation/service.py: normalize_script 발췌
def normalize_script(lines: list[ScriptLine], turns: int) -> list[Turn]:
    merged: list[ScriptLine] = []
    for line in lines:
        text = line.text.strip()
        if not text: continue
        # 같은 화자가 연속으로 말하면 한 줄로 병합하여 교대 턴 유지
        if merged and merged[-1].speaker == line.speaker:
            merged[-1] = ScriptLine(speaker=line.speaker, text=f"{merged[-1].text} {text}")
        else:
            merged.append(ScriptLine(speaker=line.speaker, text=text))

    # A(요청자)가 먼저 대화를 시작하도록 첫 발화 보정
    while merged and merged[0].speaker != "a":
        merged.pop(0)

    # 요청 턴 수(2 * turns)에 맞게 정확히 슬라이싱
    want = turns * 2
    if len(merged) > want:
        merged = merged[:want]
    return [Turn(index=i, speaker=line.speaker, text=line.text[:1000]) for i, line in enumerate(merged)]

고성능 비동기 처리: 커넥션 풀 반환 & 인플라이트 락

대본+리포트 생성은 LLM 응답에 최대 30~60초가 소요됩니다. 만약 DB 트랜잭션을 연 채로 LLM을 기다리면 asyncpg 풀(기본 15~20개)이 즉시 고갈되어 전체 서버가 마비됩니다.

me = await self._load("me", req.me_ref())
partner = await self._load("partner", req.partner_ref())
await self.db.commit() # 조회 후 즉시 커넥션을 풀에 반환!
async with _IN_FLIGHT_LOCK: # 동일 페르소나 쌍의 중복 호출 방지
    ... LLM 호출 진행 (DB 커넥션 점유 없음) ...

1:1 연습 대화 (app/features/practice/)

사용자가 상대방의 확정된 페르소나와 실시간으로 카카오톡 소개팅 대화를 연습할 수 있는 기능입니다. 네트워크 환경과 클라이언트 요구사항에 맞추어 SSE 실시간 스트리밍과 단일 JSON 응답을 동시에 완벽 지원합니다.

SSE 스트리밍 vs JSON 응답 듀얼 아키텍처 (api.py)

서비스 레이어(service.py)는 항상 AsyncIterator[(event, model)] 제너레이터를 생산하고, API 레이어가 이를 SSE 텍스트 스트림(_to_sse) 또는 한 번에 모은 JSON(collect_reply)으로 직렬화합니다.

작업 일반 JSON 엔드포인트 SSE 스트리밍 엔드포인트 설명
첫 인사 POST /{id}/opening POST /{id}/opening/stream 상대 페르소나가 먼저 인사를 건넴
답변 전송 POST /{id}/messages POST /{id}/messages/stream 내 메시지 저장 후 상대 답변 생성
답변 재시도 POST /{id}/retry POST /{id}/retry/stream 끊긴 마지막 내 메시지에 답변만 다시 수신

request 스코프 DB 세션 수명 제어 (FastAPI Dependency Scope)

FastAPI의 기본 Depends(get_db)는 라우트 함수가 반환되는 즉시 DB 세션을 닫습니다. 하지만 SSE 스트리밍은 라우트가 StreamingResponse를 반환한 후에도 제너레이터가 한참 동안 실행되면서 완료 시점에 상대 답변을 DB에 커밋해야 합니다. 

# app/features/practice/api.py 발췌
# 일반(JSON) 요청용 의존성: 함수 완료 시 세션 정리
def get_service(db: AsyncSession = Depends(get_db)) -> PracticeService:
    return PracticeService(db)

# SSE 스트리밍 요청용 의존성: HTTP 응답 스트림이 완전히 끝날 때까지 세션을 유지
def get_stream_service(db: AsyncSession = Depends(get_db, scope="request")) -> PracticeService:
    return PracticeService(db)

선저장 후스트리밍 (Save-First) & 멱등적 재시도 (/retry)

사용자 경험 보호를 위해 내 메시지를 DB에 먼저 커밋한 뒤 상대방의 스트리밍을 시작합니다.

  • 네트워크 중단 방어: LLM 스트리밍 도중 통신이 끊겨도 내 메시지는 이미 안전하게 저장되어 있으므로 새로고침해도 화면에서 사라지지 않습니다.
  • 오염 방지: 스트리밍 도중 끊긴 불완전한 조각(반 토막 답변)은 DB에 쓰지 않고 즉시 버려 다음 대화 맥락이 오염되는 것을 방지합니다.
  • /retry 엔드포인트: 답변이 누락된 마지막 메시지를 감지하여 사용자가 같은 말을 다시 타이핑할 필요 없이 상대 답변만 다시 생성합니다.

Anthropic SDK 첫 메시지 user 제약 우회 로직

Anthropic Claude 모델은 메시지 배열의 첫 번째 요소가 무조건 role: "user"이어야 합니다. 상대방이 먼저 인사를 건넨 세션은 히스토리 첫 항목이 assistant가 되어 API 오류가 발생합니다. 

# app/features/practice/service.py: _history 발췌
msgs = [{"role": "user" if m.role == "user" else "assistant", "content": m.content}
        for m in session.messages[-HISTORY_WINDOW:]]

# 첫 메시지가 assistant면 인사 지시문을 가상 user 메시지로 맨 앞에 주입!
if msgs and msgs[0]["role"] == "assistant":
    msgs.insert(0, {"role": "user", "content": OPENING_INSTRUCTION})

핵심 엔지니어링 패턴 총정리

도메인 간 페르소나 격리 (lookup.py & profile.py)

시뮬레이션과 연습대화는 온보딩 서비스 내부 구현을 직접 참조하지 않고, load_persona(db, ref) 단일 진입점만을 통해 페르소나를 읽어옵니다.

또한 profile.py의 describe() 함수는 점수표(숫자)를 LLM이 연기할 수 있는 자연어 프로필 문장으로 변환합니다. 이때 사용자가 입력한 MBTI는 말투 힌트(MBTI_TONE)로만 약하게 사용되며, 온보딩 대화에서 검증된 답변 성향이 항상 최우선시됩니다.

엔터프라이즈 Langfuse 분산 관측성 (observability.py)

개별 비즈니스 코드가 Langfuse 예약어를 직접 핸들링하지 않도록 build_langfuse_metadata 팩토리를 제공합니다.

모든 LLM 호출에는 feature, operation, user_id, session_id가 일관되게 주입되며, 컨텍스트 매니저(propagate_langfuse_metadata)를 통해 하위 트레이스로 안전하게 전파됩니다.

견고한 장애 격리 (Graceful Fallback)

외부 LLM API(OpenRouter, Anthropic 등)가 일시적 장애를 겪더라도 서비스가 중단되지 않는 3중 안전장치가 구축되어 있습니다.

  • 온보딩: LLM 추출 실패 시 선택지 기반 규칙 초안(fallback_extraction) 자동 생성.
  • 시뮬레이션: LLM 타임아웃 시 규칙 점수 기반 템플릿 서술(_template_narrative) 즉시 조립.
  • 연습대화: 첫 조각 수신 실패 시 안전 폴백 인사말(FALLBACK_REPLY) 전송.

무침습 로컬 플레이그라운드 (dev/)

개발 및 테스트용 dev/ 모듈은 프로덕션 코드(app/)를 단 한 줄도 수정하지 않습니다.

FastAPI의 dependency_overrides[get_db]를 통해 SQLite 비동기 인메모리 DB로 교체하고, 모듈 속성 바인딩(bind_call, bind_stream)을 통해 요청 헤더의 Gemini/Anthropic 키로 LLM 엔진을 런타임에 동적 교체합니다.

아키텍처 설계 핵심 요약

별이삼샵 AI API는 비즈니스 로직과 LLM 생성 책임을 철저히 분리함으로써, LLM의 비결정론적 특성을 최소화하고 시스템의 신뢰성과 응답성을 극대화한 프로덕션 급 아키텍처입니다. 특히 점수 산정의 결정론적 보장, DB 커넥션 풀 선제적 반환, FastAPI 생명주기를 고려한 SSE 스트리밍 설계는 AI 서비스 엔지니어링의 모범적인 패턴을 보여줍니다.
